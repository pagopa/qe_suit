# Reporting Tool - Design Notes

Last update: 2026-09-24 (architecture + implementation decisions v1.5)

## Goal
Build a reporting tool in `common` that reads Surefire XML reports and generates a human-readable HTML report.

## Agreed Scope
- Primary input: Surefire XML files (`TEST-*.xml`) from `target/surefire-reports`.
- Primary output: one self-contained `.html` file (human-readable).
- IntelliJ native integration is not a priority for now.
- Focus on Maven/Surefire flow first.

## Data Source Strategy
- Use XML as the primary structured source of truth.
- Do not rely on raw console logs as primary source.
- Extract logs from `<system-out>` inside each `<testcase>`.

## Target Navigation Model (3 levels)
1. Test class
2. `@TestFactory` method
3. Concrete runtime test case(s) generated by factory

All levels must be:
- Navigable
- Filterable
- Aggregated with counters/durations

## How to identify levels
### Level 1 - Test class
- From `<testcase classname="...">`.

### Level 2 - TestFactory method
- From `<testcase name="...">` using pattern like `methodName()[index]`.
- Parse factory method with regex (draft):
  - `^(?<factory>.+)\(\)\[(?<idx>\d+)\]$`

### Level 3 - Concrete case
- Parse log content inside `<testcase>/<system-out>`.
- Detect case markers such as:
  - `REPLACED_WITH_NULL @ <root>`
  - `REMOVED @ /name`
- If multiple concrete cases are found in the same testcase, split testcase logs into N case logs.
- Use `timestamp + thread` as support to reduce ambiguity when lines are interleaved.
- Fallback when no marker is found: `UNKNOWN_CASE`.

## Privacy and property filtering
Keep only non-sensitive properties useful for debug.

### Keep (examples)
- Java runtime/version/vendor info
- OS name/version/arch
- locale/timezone/encodings
- test/app identifiers

### Exclude (always)
- local absolute paths
- usernames/home/work directories
- classpaths and repository paths
- temp dirs, process ids, launcher commands

## Proposed MVP features
- Run summary (tests, failures, errors, skipped, total time)
- Tree navigation: class -> factory -> concrete case
- Filters: status, text search, only failing
- Duration ordering/highlight of slow tests
- Failure/error detail with collapsible stacktrace
- Safe environment/properties section
- Single self-contained HTML output

## High-level architecture (agreed direction)
- DTO Java as canonical in-memory representation of report data.
- Parser component: reads input and maps to canonical DTO.
- Writer component: renders output from canonical DTO.
- Main orchestrator: wires parser + writer and runs the pipeline.

### Canonical DTO scope (confirmed)
- DTO contains only selected/approved fields needed for report and debug.
- DTO must not include extra parser-only details or machine-private data.
- This keeps writer simpler and reduces privacy risk by construction.

### Components and contracts
- `ReportParser` (interface)
  - responsibility: parse a source and build canonical DTO.
  - pluggable implementations: `SurefireXmlReportParser` today, others tomorrow.
- `ReportWriter` (interface)
  - responsibility: write output from canonical DTO.
  - pluggable implementations: `HtmlReportWriter` today, others tomorrow.
- `ReportingMain` (entry point)
  - responsibility: parse CLI args/options, select parser/writer, orchestrate flow, handle errors.

### Coupling minimization strategy
- Writers must depend only on canonical DTO, never on parser-specific classes.
- Parsers must not know writer internals or output format details.
- Keep parser-specific extraction details in dedicated adapter classes.
- Use immutable DTOs where possible to stabilize contracts.
- Prefer additive DTO evolution (new optional fields) to avoid breaking writers.

### Proposed package layout (under `it.pagopa.reporting`)
- `dto` -> canonical report model
- `parser` -> parser interfaces
- `parser.surefire` -> Surefire XML parser implementation
- `writer` -> writer interfaces
- `writer.html` -> HTML writer implementation
- `app` -> orchestrator / main / CLI options

### Notes on DTO stability
- Goal: if input source changes, replace parser only.
- Goal: if output style/format changes, replace writer only.
- Constraint acknowledged: when canonical DTO contract changes, writer changes may be needed.
- Mitigation: define DTO v1 carefully and evolve with backward-compatible optional fields.

### Writer strategy (agreed)
- Preserve explicit semantic tree for navigation: class -> factory -> concrete case.
- Reflection/introspection is allowed as a rendering technique, but on curated DTO only.
- Prefer hybrid rendering:
  - semantic sections for primary UX and filters
  - optional recursive dump panel for advanced debug details
- Writer must remain parser-agnostic and depend only on DTO contract.

### Annotation-driven rendering (proposal)
- Main idea: annotate DTO fields/types with rendering metadata, similar to Jackson-style mapping.
- Expected benefit: writer can infer UX placement without parser coupling.
- Suggested annotation intents:
  - semantic role (run/class/factory/case)
  - label and display order
  - formatting hints (duration/status/code block)
  - filtering/index keys
  - hidden/redacted flags for sensitive values
- Validation step in writer startup:
  - verify required semantic nodes are present
  - fail fast on invalid/missing annotation combinations
- Keep a fallback convention (name/type-based) for backward compatibility while annotations evolve.

## Parsing principles
- Be deterministic: same input -> same output.
- Be lossless for failures: never drop failure/error data.
- Be defensive: tolerate missing tags/fields.
- Keep raw snippets available for troubleshooting.

## UX decisions agreed on 2026-09-24 (implemented)
- Keep current sidebar code path available, but hide/collapse it by default in the UI.
- Move primary navigation to the main page panel with explicit hierarchical expansion:
  1. class
  2. factory
  3. concrete case
- Navigation must be fully expandable (class -> factories -> cases) and visible without requiring a side column.
- Introduce aggregate status coloring at class/factory level:
  - green only if **all** nested items are `PASSED`
  - dark red if at least one nested item is `ERROR`
  - red (lighter than ERROR) if there is at least one `FAILED` and no `ERROR`
  - yellow if there are no `FAILED`/`ERROR` and at least one `UNKNOWN` or `SKIPPED`
  - precedence: `ERROR` > `FAILED` > `UNKNOWN|SKIPPED` > `PASSED`
- Keep a compact per-node status badge (e.g. `F:x E:y U:z S:w`) to make aggregate color decisions explicit.
- In details area, render concrete cases by factory using a 2-column table:
  - column 1: test/case name
  - column 2: status
- Keep filters unchanged (`Search` + status checkboxes).
- Use a softer, less saturated palette for status and navigation colors.

## UX corrections agreed on 2026-09-24 (design phase, pending implementation)
- Concrete case interaction must be inline-only:
  - clicking a concrete case expands/collapses details in place
  - no anchor jump to another page position for case details
- Case-level links in navigation can be removed/replaced with direct inline toggle behavior.
- Remove duplicated detailed section currently rendered below navigation (`Class -> Factory -> Concrete case`) and keep a single primary expandable view.
- Section order after header must be:
  1. `Run summary`
  2. `Filters`
  3. `Navigation`
- Page/report title must be renamed from `Surefire HTML Report` to `QE SUIT Contract Test HTML Report`.

## Implementation decisions v1

### Minimal annotation set
- `@ReportNode(role, label)` on DTO types to express semantic role.
- `@ReportField(label, order, format, filterable)` on DTO fields/record components.
- `ReportNodeRole` enum: `RUN`, `SUMMARY`, `TEST_CLASS`, `TEST_FACTORY`, `CONCRETE_CASE`, `PROPERTY`.
- `ReportFieldFormat` enum for rendering hints: `AUTO`, `INTEGER`, `DECIMAL`, `DURATION_SECONDS`, `STATUS`, `MULTILINE`, `CODE_BLOCK`.

### Regex strategy (implemented)
- Factory extraction from testcase name:
  - `^(?<factory>.+)\(\)\[(?<idx>\d+)]$`
  - fallback for non-matching names: treat testcase name as factory name (factory-level testcase)
- Concrete case marker extraction from testcase log:
  - `(?<scenario>[A-Z][A-Z0-9_]+)\s+@\s+(?<target><root>|/[^\s:]+)`
- Thread extraction for interleaving support:
  - `^\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}\.\d{3}\s+\[(?<thread>[^]]+)]`
- Failure correlation markers from stacktrace/failure text:
  - `(?m)^\s*-\s*scenario:\s*(?<scenario>[A-Z][A-Z0-9_]+)\s*$`
  - `(?m)^\s*-\s*targetPath:\s*(?<target>[^\r\n]+)\s*$`

### Concrete case split policy
- Parse `<system-out>` line-by-line.
- Track active case per thread after marker detection.
- Append lines to the active thread-case stream.
- Non-attributed lines are preserved in `UNKNOWN_CASE`.
- If no case marker is found, create a single `UNKNOWN_CASE` with full testcase log.
- For non-dynamic testcase names (without `[index]`), do not split by marker: create one explicit concrete case bound to that testcase/factory. This preserves `@TestFactory` discovery/runtime errors as visible red entries instead of grouping them under `UNKNOWN_FACTORY`.

### HTML output format (implemented)
- Self-contained single HTML file.
- Main panel includes expandable navigation tree `class -> factory -> concrete case`.
- Legacy sidebar renderer is preserved in code path for fallback and is not active by default.
- Detailed section renders concrete cases per factory in a 2-column table:
  - column 1: test/case name with expandable row toggle
  - column 2: status
- Aggregate class/factory color semantics with precedence:
  - dark red when `ERROR` exists
  - red when `FAILED` exists and no `ERROR`
  - yellow when no `FAILED`/`ERROR` but `UNKNOWN` or `SKIPPED` exists
  - green only when all nested items are `PASSED`
- Compact aggregate counts badge (`F/E/U/S`) shown near class/factory labels.
- Softer visual palette for status and hierarchy styling.
- Global filters (client-side JS):
  - free text search
  - status checkboxes (`PASSED`, `FAILED`, `ERROR`, `SKIPPED`, `UNKNOWN`)
- Hierarchical visibility propagation:
  - hide navigation/class/factory nodes when no visible child case remains after filter.
- Row-level expandable details for stacktrace and case log.
- Optional annotation-driven recursive DTO dump panel for deep debug.

### HTML UX revision status

### CLI and orchestration (implemented)
- Entry point: `ReportingMain`.
- CLI options:
  - `--input` / `-i` (required)
  - `--output` / `-o` (optional)
  - `--no-dto-dump` (optional)
- V1 orchestration policy:
  - fixed parser: `SurefireXmlReportParser`
  - fixed writer: `HtmlSidebarReportWriter`

### Operational usage and output path behavior (implemented)
- Typical invocation:
  - `java it.pagopa.reporting.app.ReportingMain --input <surefire-xml-or-directory> --output <report.html>`
- Output resolution:
  - with explicit `--output`, write to that exact path
  - without `--output` and directory input, write `<input>/surefire-html-report.html`
  - without `--output` and file input, write next to input file using the same base name and `.html` extension
- On successful generation, the CLI prints the resolved output path (`Report generated: ...`).
